02 — Reliability under backlog

The queue changes what “now” means.

A bounded poll must preserve receive-time order. Checking the wall clock before processing pending frames can report an outage that never happened.

EXPLANATORY TEST INPUTS

16 frames remain. No false timeout.

The first batch arrives at 0 ms. While it is processed, mocks enqueue another batch at 3, 6, …, 48 ms. Each gap is below the 32 ms limit.

Pending after poll 116 / 16 slots
✓Defer wall-clock check. Keep arrival order.

Poll 2 processes those timestamps without a timeout. These are controlled mock inputs, not measured hardware timings.

01

Bound the work in main context

Drain at most 16 frames. Validation and blocking UART stay outside the CAN interrupt callback.

02

Take an atomic empty-queue snapshot

Only use the current tick for timeout checking once the queue is empty. Preserve the caller’s interrupt mask.

03

Still detect a real gap

When the next queued arrival is at 40 ms, the next poll reports the real gap beyond 32 ms and then accepts recovery traffic.

04

Prove behavior, name the limit

Captured HAL tests below cover backlog, rollover, overflow, and recovery. CPU scheduling and physical CAN/UART behavior require board evidence.

Presenter notesa five-minute walkthrough
0:00–1:00
Define the boundary
“This is a project demonstration using recorded host execution. The portable C11 core validates an eight-byte Classic CAN payload, while the STM32 adapter queues arrivals and forwards accepted samples to UART.” Start with nominal traffic and point to the bytes, status, and exact UART row.
1:00–2:00
Diagnose the fault
Choose CRC corruption, then semantic range. A bad CRC rejects accidental corruption. A recomputed CRC does not make an impossible engineering value valid. Explain the next sequence rejection after the lost accepted sample, then show recovery.
2:00–3:00
Explain a reliability decision
Show sequence discontinuity and timeout. A valid unexpected sequence becomes the new baseline but is not forwarded. Timeout measures time since acceptance; it is an event, not a blanket rejection of the next valid frame. Use the captured event log to show the elapsed interval.
3:00–4:00
Discuss the hard edge case
Walk through the explanatory backlog example. Polling is bounded; queued timestamps must be evaluated before the current clock. Explain the atomic empty-queue snapshot, the real-gap regression, and tick rollover. Distinguish these controlled inputs from measured interrupt timing.
4:00–5:00
Close with evidence and next steps
Open the HAL case list and raw log. Explain queue overflow and UART failure policy, then name remaining work: build with the actual Cube HAL, collect paired CAN/UART captures, and measure blocking UART before choosing DMA. Download the evidence for review.
Follow-up
Be precise about the claim
“I can demonstrate the behavior in host tests and explain the design trade-offs. I have not established physical-layer performance, production suitability, or certification.” This walkthrough is project evidence, not a claim about an employer’s requirements.
